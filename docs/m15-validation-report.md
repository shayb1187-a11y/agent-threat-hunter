# M15: what real telemetry changed

Status: measurements taken 2026-09-12 at commit `d08cdd2`. The "before" column is
commit `ddca219`, the M14 checkpoint, re-run from a clean worktree rather than copied
out of the M14 report. Every number here is regenerated by `scripts/m14_profile.py`,
`scripts/m14_incident.py` or `python main.py benchmark`; the JSON records are under
`reports/m14/` (before) and `reports/m15/` (after).

## The short version

On synthetic fixtures the system looked perfect: every incident passed, recall was
100%, and the benchmark had been green for six milestones. Pointing it at telemetry it
did not generate produced **seven distinct failures**, two of which would have made it
unusable in a real SOC — 67.5 false positives per day from a quiet Windows estate, and
2,070 per day from a Kubernetes cluster doing nothing wrong.

None of those failures were visible in the synthetic suite, and none of them were
threshold problems. Each was a rule asserting something the telemetry did not support.

## The headline

### False positives on real, benign telemetry

Every finding on these corpora is a false positive by construction: the datasets contain
no attack. Ingestion is byte-identical before and after — the same events reach the
rules, and what changed is what the rules conclude from them.

| Corpus | Events | Before | After |
| --- | --- | --- | --- |
| DEDALE benign day 3 (30 hosts, 11 h) | 58,279 | 30 findings — **67.5/day**, 30 singleton cases | **0 findings, 0 cases** |
| Kubernetes CI e2e audit (38 min) | 7,951 | 55 findings — **2,070/day**, 55 singleton cases | **0 findings, 0 cases** |
| flaws.cloud CloudTrail (3.7 years) | 79,520 | 39 findings, **39 singleton cases** | 39 findings, **4 cases** |
| DEDALE attack day 15 | 49,276 | 30 findings, **30 noise cases** | **0 findings, 0 noise cases** |

flaws.cloud is the honest one in that table: the **finding** count did not move. What
moved is the analyst-facing **case** count, 39 → 4, because a failed-logon burst that
never succeeded is no longer graded HIGH and explained findings no longer raise a case
on their own.

### Attack recall on the synthetic benchmark

The reason the table above is not simply "we turned the rules off".

| Metric | Before (`ddca219`) | After (`d08cdd2`) |
| --- | --- | --- |
| Incidents meeting their success condition | 5 / 5 | 5 / 5 |
| INC-001 event recall | 100% (31/31) | 100% (31/31) |
| INC-002 event recall | 93% (13/14) | 93% (13/14) |
| INC-004 event recall | 100% (6/6) | 100% (6/6) |
| INC-005 event recall | 100% (2/2) | 100% (2/2) |
| Attack-stage coverage | 12 / 12 | 12 / 12 |
| **INC-004 chain recall** | **50%** | **100%** |
| INC-001 findings → cases | 13 → 2 | 13 → **1** |
| INC-004 findings → cases | 4 → 3 | 4 → **1** |

Per-rule, the three rules whose real-data behaviour changed still detect what they are
for: `ATH-001`, `ATH-004` and `ATH-005` each score 1 true positive and 0 false positives
on the Windows benchmark, and `K8S-001`/`K8S-002` carry INC-005 at 100% recall.

## The seven failures, and what each one actually was

| # | Failure | Root cause | Fix |
| --- | --- | --- | --- |
| 1 | 30 `ATH-004` findings/day on a benign estate — every host, every boot | The rule matched `lsass.exe`'s **own** image path, so LSASS starting counted as something accessing LSASS | `ATH-004` reads argv[0] and no longer matches the target's own process (`c99b5f6`) |
| 2 | 36 `ATH-005` findings graded HIGH on a 3.7-year CloudTrail trail | A failed-logon burst was graded on volume alone, with no term for whether anything ever succeeded | A burst with no success is MEDIUM (`2883ee8`) |
| 3 | 55 `K8S-001` findings in 38 minutes — every `cluster-admin` binding in a CI cluster | The rule fired on the *grant*, ignoring who was granting. All 55 were by `system:masters` members, whom the authorizer already allows everything before RBAC is consulted | `K8S-001` reads the grantor's standing; a grant that escalates no one relative to the grantor is silent (`ba5e5b3`) |
| 4 | `ATH-001` blind to LibreOffice | `OFFICE_APPLICATIONS` was a Microsoft-only list | LibreOffice added (`221e870`) |
| 5 | Triage had 0% purchase on real data — 124 of 124 findings vetoed | Everything real arrived HIGH+, and the benign layer is not allowed to clear HIGH+ | Boundary deliberately kept; the 124/124 was downstream of failures 1–3, and is pinned per corpus so it cannot silently return (`4081332`) |
| 6 | Explained false positives still raised cases | Correlation ran before triage's verdict was consulted | Findings triage has explained no longer raise a case on their own (`285b762`) |
| 7 | **INC-004 chain recall 50%** — one operator's session split across two cases | Correlation knew parent→child but had no relation for **siblings** under a parent that is itself no finding | `sibling_lineage`, gated on parent fan-out and child-spawn span read off the telemetry (`d08cdd2`) |

Failures 1–3 share a shape worth naming: each rule was keying on **an event that
occurred** rather than on **a claim the event supports**. LSASS starting is not LSASS
being read; a burst of failures is not a compromise; a privileged grant by someone
already fully privileged escalates nobody.

## What this does not show

Stated because the table above is flattering and a reader deserves the other half.

**DEDALE's attack day was never detected, before or after.** Event recall there is
**0 of 5, unchanged**. The false positives are gone, but nothing replaced them: 9,562 of
9,567 labelled malicious events live in channels ATH has no table for. The before column
records one conclusion hit (`CLIENT2`) — that was an accident, the hostname surfaced by
one of the 30 false positives, and it disappeared along with them. A fake win
disappearing is progress, but it is not a real win appearing.

**The benign corpora cannot prove recall.** DEDALE day 3, the CI cluster and K8NTEXT
contain no attack, so they can only ever measure false positives. That the fixed rules
still fire is evidenced elsewhere — the synthetic incidents, 13 positive-control tests,
and adapter-spliced attacks — not by these corpora.

**Two datasets remain unmeasured.** Kubernetes + injected Stratus attacks is blocked (no
Docker, kind, kubectl or Stratus on this machine) and BOTS v3 is pending a Splunk export.
Both would test recall on real telemetry, which is exactly the gap above.

**One corpus, one cluster, one estate.** 67.5/day and 2,070/day are measurements of two
specific environments over 11 hours and 38 minutes respectively. They justify the fixes;
they do not establish a general false-positive rate.

## Remediation checkpoint: xfails, tradeoffs, and what comes next

**Strict xfails.** M14 left 11; all 11 are retired, each in the commit that fixed its
defect, with the pinned measurement updated in the same change. None remain. The one that
did not flip as written was "triage has purchase on a benign corpus": once the DEDALE hour
yielded no findings it could never pass and stated the wrong target, so it was replaced by
a per-corpus count of findings vetoed by severity (0/0/1 findings, 0 vetoed) and a pin that
the one remaining real finding, a no-success guessing burst, is `needs_review` -- the
honest verdict, not a defect. The gap the benign layer still has is a signal that reads
logon evidence; that is missing evidence, not the HIGH boundary.

**Tradeoffs stated, not hidden.** A `cluster-admin` binding created by a `system:masters`
superuser and never used is no longer surfaced by `K8S-001` on its own; before, it was one
of 2,070/day and not actionable either, and `K8S-002` still fires the moment the grantee
uses the grant. A failed-logon burst with no success is an alert at MEDIUM, not a case.
Neither cost a labelled true positive anywhere in the suite or on real data.

**One representational change.** The control table gained `actor_groups` (the caller's
asserted groups, comma-joined; empty for CloudTrail). It carries a field the Kubernetes
adapter already parsed and dropped, and it is what let `K8S-001` read the grantor's
standing instead of guessing from how often a grant recurs. Not a new channel or table.

**Next priority: detection coverage before representation expansion, narrowly.** T1036
(unsigned, system-like name from a user-writable path) and T1547.001 (Run-key write) are
representable in the process table today and would move DEDALE's attack-day recall from
0 of 5 toward 4 of 5 -- the first true-positive case on real telemetry, which M14 named as
the precondition for the LLM arm meaning anything. With the benign corpora now silent,
their false-positive cost is measurable the day they land. Representation (PowerShell
4103/4104, Kubernetes `serviceaccounts/token` and `secrets`) follows: it needs both a
table and rules that read it before it moves anything measurable.
